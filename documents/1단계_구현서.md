# 1단계 구현서: 루트 DNS 서버에 직접 질의하기

## 1. 구현 결과

1단계에서는 고정된 도메인 `www.example.com.`에 대해 루트 DNS 서버에 직접 질의하고, `.com` TLD DNS 서버 정보를 받는 과정을 구현했다.

질의는 먼저 UDP로 보낸다. 응답 헤더의 `TC` 플래그가 켜져 있으면 UDP 응답이 잘린 것이므로, 같은 DNS 메시지를 TCP로 다시 보내 전체 응답을 받는다.

```text
www.example.com. IN A 요청 생성 (RD=0)
→ a.root-servers.net.에 UDP 질의
→ TC 플래그 확인
→ TC가 있으면 TCP로 같은 질의 재전송
→ .com TLD의 NS 및 glue 레코드 확인
```

루트 서버는 `www.example.com.`의 IPv4 주소를 직접 관리하지 않는다. 따라서 응답의 `Answer` 섹션은 비어 있고, `Authority` 섹션에 `.com`을 담당하는 TLD DNS 서버 목록이 들어온다.

## 2. 실제 구현 범위

| 항목 | 구현 내용 |
| --- | --- |
| 언어와 라이브러리 | Python과 `dnspython`을 사용했다. |
| 질의 대상 | `a.root-servers.net.`의 IPv4 주소 `198.41.0.4`를 사용했다. 이 주소는 [IANA Root Servers](https://www.iana.org/domains/root/servers) 정보로 확인했다. |
| 도메인 | 학습용 예시인 `www.example.com.`을 코드에 고정했다. |
| 질의 종류 | 최종 목표가 IPv4 조회이므로 A 레코드를 요청했다. |
| 재귀 요청 | `flags=0`으로 RD 비트를 끄고, 루트 서버가 아는 위임 정보만 받도록 했다. |
| 전송 방식 | UDP를 먼저 사용하고, `TC`가 있으면 TCP로 다시 질의한다. |
| 출력 | `print(response)`로 DNS 응답 전문을 출력해 각 섹션을 직접 확인한다. |

현재 코드는 [root_query.py](../root_query.py)에 있다.

## 3. 핵심 코드와 동작

### 3.1 DNS 요청 메시지 만들기

```python
domain = "www.example.com."

query_message = dns.message.make_query(
    qname=domain,
    rdtype="A",
    flags=0,
)
```

`qname`은 질문할 도메인 이름이고, `rdtype`은 원하는 레코드 종류다. 여기서 A는 IPv4 주소 레코드를 뜻한다.

`flags=0`은 DNS 요청의 플래그를 모두 끈다. 특히 RD(Recursion Desired)가 꺼지므로, 루트 서버에 최종 답을 대신 찾아 달라고 요청하지 않는다. 루트 서버가 알려 주는 다음 질의 대상, 즉 TLD DNS 서버 정보를 직접 받기 위한 설정이다.

초기 계획서에는 `want_recursion=False` 예시가 있었지만, 현재 사용 중인 `dnspython 2.8.0`의 `make_query()`는 이 인자를 지원하지 않는다. 실제 구현에서는 `flags=0`을 사용했다.

### 3.2 UDP로 루트 서버에 질의하기

```python
response = dns.query.udp(
    query_message,
    ROOT_SERVERS[0]["ipv4"],
    timeout=3.0,
)
```

`query_message`는 앞에서 만든 DNS 요청이고, 두 번째 값은 요청을 보낼 루트 서버 IP 주소다. `timeout=3.0`은 응답을 최대 3초 기다린다는 뜻이다.

일반 DNS 질의는 보통 UDP를 사용한다. 요청과 응답이 작고, 연결을 먼저 만들 필요가 없기 때문이다.

### 3.3 TC 플래그를 확인하고 TCP로 다시 질의하기

```python
if response.flags & dns.flags.TC:
    response = dns.query.tcp(
        query_message,
        ROOT_SERVERS[0]["ipv4"],
        timeout=3.0,
    )
```

`response.flags`는 DNS 헤더의 여러 상태를 비트로 담은 값이다. `dns.flags.TC`는 그중 TC 비트의 위치만 표시한 비트마스크다.

```text
response.flags & dns.flags.TC
```

이 결과가 0이 아니면 TC 비트가 켜진 상태다. TC는 TrunCation의 약자로, UDP 응답이 전송 채널의 크기 제한 때문에 잘렸음을 뜻한다.

`www.example.com.` 질의에서는 `.com` TLD 서버 13개의 NS 레코드와 그 서버들의 IP 주소가 응답에 포함되어 UDP 응답이 잘렸다. TCP는 더 큰 DNS 메시지를 전달할 수 있으므로, 같은 요청을 TCP로 다시 보내 전체 응답을 받았다.

## 4. 응답에서 확인한 내용

루트 서버의 응답에는 아래 항목이 나타났다.

| 항목 | 의미 |
| --- | --- |
| `rcode NOERROR` | 루트 서버가 질의를 정상적으로 처리했다. 최종 IP를 찾았다는 뜻은 아니다. |
| `QR` | 현재 메시지가 서버의 응답임을 뜻한다. |
| `TC` | UDP 응답이 잘린 상태다. TCP 재질의가 필요하다. |
| `QUESTION` | `www.example.com. IN A`라는 원래 질문이다. |
| `ANSWER` | 루트 서버는 최종 IP를 관리하지 않으므로 비어 있는 것이 정상이다. |
| `AUTHORITY` | `.com`을 담당하는 TLD DNS 서버의 NS 레코드 목록이다. |
| `ADDITIONAL` | TLD DNS 서버의 A/AAAA 주소인 glue record다. |
| `172800` | TTL이며, 172800초는 2일이다. |

TCP 재질의 후에는 `TC`가 없는 완전한 응답을 받았다. 이 응답의 `Authority`와 `Additional` 정보는 2단계에서 TLD DNS 서버를 선택할 때 사용하게 된다.

## 6. 이번 단계에서 보류한 내용

다음 항목은 구현하지 않았다.

- 사용자 입력과 도메인 형식 검증
- 전체 IANA root hints 목록 및 다른 루트 서버 재시도
- NS 및 glue 레코드만 골라 사람이 읽기 좋게 출력하는 형식화
- 시간 초과, 네트워크 오류, `NXDOMAIN` 등의 예외 처리
- TLD DNS 서버와 권한 DNS 서버에 이어서 질의하기
- 최종 A 레코드와 IPv4 주소 출력

사용자 입력, 다중 루트 서버, 오류 처리는 도구의 사용성을 높이지만, 이번 단계에서 확인하려는 DNS 메시지 생성·직접 질의·응답 해석에는 필수로 두지 않았다. TLD 추적과 최종 IP 조회는 2단계 이후의 작업이다.

## 7. 완료 기준

이번에 합의한 1단계의 구현 범위에서는 아래 조건을 모두 만족했다.

- 루트 DNS 서버의 IP 주소로 DNS 요청을 직접 전송했다.
- `www.example.com. IN A` 요청에서 RD 비트를 끄고 위임 응답을 받았다.
- UDP 응답의 TC 플래그를 비트마스크로 확인했다.
- TC가 있으면 TCP로 같은 요청을 재전송해 전체 응답을 받았다.
- 응답의 `Authority`에서 `.com` TLD의 NS 레코드를, `Additional`에서 glue record를 확인했다.

따라서 고정된 예시 도메인으로 루트 DNS 서버에 직접 질의하는 구현은 완료했다. 사용자 입력과 여러 root hints 지원은 이후 필요할 때 별도 작업으로 추가한다.

## 8. 실행 방법

가상환경을 활성화한 뒤 다음처럼 실행한다.

```powershell
python root_query.py
```

출력된 DNS 응답에서 `AUTHORITY`와 `ADDITIONAL` 섹션을 확인한다. UDP 응답이 잘린 경우에는 TCP 재질의 결과가 출력된다.
